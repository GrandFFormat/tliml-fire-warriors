# This Land Is My Land — Modding Knowledge Base

Everything learned while building the "Fire Warriors" BepInEx mod for *This Land Is My Land* (Steam). This is written for whoever (human or Claude) picks up work on this mod, or any other mod for this game, next. It captures the game-engine facts, gotchas, and workflow that took real trial-and-error to discover, so nobody has to rediscover them from scratch.

The mod's own version history/changelog and current feature list live in `README_FireWarriors.txt` — this document is deliberately different: it's the reusable *technical* knowledge, not a changelog.

## Project setup

- Game: *This Land Is My Land*, Unity **2018.2.21f1**, **Mono** scripting backend (not IL2CPP) — this matters because normal .NET reflection works fine at runtime; nothing needs an IL2CPP-aware reflection shim.
- Mod framework: **BepInEx 5.4.23.5**, plus **HarmonyLib 2.x** for patching.
- Install path used throughout: `C:\Program Files (x86)\Steam\steamapps\common\This Land Is My Land`. Compiled plugin goes in `BepInEx\plugins\`.
- No IDE/MSBuild project was used — compilation is a single `mcs` (Mono C# compiler) invocation via a shell script, run from a Linux dev environment. See `compile.sh`.
- Reference DLLs are extracted directly from the game's own `This Land Is My Land_Data\Managed\` folder (staged over from the user's machine as needed) — there is no public SDK. If you hit `CS1070`/`CS0246` ("type has been forwarded to an assembly that is not referenced") for any `UnityEngine.*` type, the fix is always the same: find the specific `UnityEngine.<X>Module.dll` that defines it in `Managed\`, copy it into the refs folder, and add a `-r:` line to `compile.sh`. This came up for `UnityEngine.ParticleSystemModule.dll` (needed for `ParticleSystem[]`) and `UnityEngine.PhysicsModule.dll` (needed for `Physics`/`Collider`).

## Toolchain / research workflow

- **`all_types.txt`** — a full IL type dump of the game's assemblies (class names, fields, methods, enum values, interfaces). This was the primary research tool for the entire project — when you need to know what a class looks like, `grep` this file first before guessing.
- **`DumpBody.exe`** — a small dumper used specifically to read the IL *inside* method bodies, which most decompilers hide by default for compiler-generated types. This mattered most for coroutines: a method like `PlayerActions.BurnSettlement(...)` is just a tiny stub in the decompiled view — the real logic lives in a hidden nested type like `PlayerActions/<BurnSettlement>c__Iterator25::MoveNext()`, and you need a body dumper to actually see what it does (in this case, that it sets `interacting`/`canMoveOrFaceToDirection` and calls `BeginInteraction()`/`EndInteraction()`).
- **Debug logging**: the mod writes to its own `FireWarriors_debug.txt` (in addition to BepInEx's normal console/log). Gate any verbose, per-frame, or per-object diagnostic dump behind a `static bool LoggedXxxDiagnostic` flag that's set `true` the first time it fires — this gets you the one detailed sample you need to diagnose a bug without flooding the log across an entire play session (used for the "nothing found" seek diagnostic and the "why did this warrior give up" stall diagnostic).
- **Iteration loop**: edit `.cs` → `bash compile.sh` → deliver the `.dll` → write it into `BepInEx\plugins\` on the user's machine → user relaunches/tests → user pastes back a `FireWarriors_debug.txt` excerpt → diagnose from real data → repeat. Don't guess ahead of what a real log shows; several early hypotheses in this project (a registration-timing bug, a missing AI component type) were self-corrected by testing against actual diagnostic output rather than theorizing further.
- **Config file gotcha**: BepInEx `.cfg` files are written with Windows line endings (`\r\n`). A `sed` pattern like `s/^Foo = 10$/Foo = 5/` will silently fail to match a real line ending in `\r` — include `\r` explicitly in the pattern (`s/^Foo = 10\r$/Foo = 5\r/`) or edit some other way that's line-ending-aware.

## Game architecture facts (This Land Is My Land specifically)

**The game destroys BepInEx plugin components shortly after startup — never drive a mod from your own `Update()`.** Every plugin here ends up logging some form of "Plugin component destroyed by the game (normal for this title)". The C# object itself survives (fields, config entries, subscriptions are all intact); only Unity's MonoBehaviour side is gone, so `Update()`, `OnGUI()`, `StartCoroutine` on that GameObject and anything else Unity drives simply stop, with **no exception and no log line**. A mod written the ordinary way therefore appears to load perfectly and then do nothing at all, forever — the failure is completely silent, and it looks exactly like a logic bug in whatever the mod was supposed to do first.
  - The fix used by every mod here: put the per-frame work in a Harmony postfix on one of the game's own methods that is guaranteed to run. `PlayerActions.Update` is the natural choice for anything player-related (it only ticks once a character exists, which is usually exactly when a mod has work to do); `AdvancedMonoBehaviourManager.Update` in the firstpass assembly is the game's master simulation tick, useful as a second, independent trigger when you also need to run while `PlayerActions` isn't active. Reach the plugin's state through a `static Instance` set in `Awake`.
  - **In that postfix, test `ReferenceEquals(Instance, null)`, never `Instance != null`.** Once the component has been destroyed, Unity's overloaded `==` reports a perfectly valid C# reference as null, so the ordinary null check skips the body forever — silently, with no exception. This has bitten this project more than once.
  - `OnDestroy` must not tear anything down. Disposing a `FileSystemWatcher`, unsubscribing from events or clearing caches there kills features that were still working, because destruction is a normal startup event rather than a shutdown. Keep such objects in `static` fields and let `OnDestroy` do nothing but log.
  - `DontDestroyOnLoad(this.gameObject)` in `Awake` does *not* prevent this and is not a substitute for the Harmony hook.

**Entity streaming is distance-based, and it's not a bug.** `Entity.AllEntities` (and almost certainly the equivalent lists for items/containers/animals) is populated via each object's own `OnEnable()` — meaning anything the game hasn't currently streamed in near the player simply isn't in that list yet. A mod scanning for "the nearest friendly NPC" or "loot within range" can come back completely empty not because of a bug, but because the player is standing somewhere the game hasn't loaded the relevant objects into. Confirmed conclusively in this project via `Physics.OverlapSphere` root-object dumps at the exact spot a search was failing — the only things nearby really were terrain/foliage/wildlife, because the player was ~200m from any camp with the nearby enemy camp already cleared out.

**`AINavMeshHumanoid` is the only humanoid AI class in the game.** There's no separate "camp worker"/"villager" class — every human NPC, friendly or hostile, uses this one `MonoBehaviour`. Relevant fields/members:
- `NavMeshAgent agent` — the actual pathfinding component.
- `BehaviorDesigner.Runtime.BehaviorTree behaviorTree` (private) and `BehaviorDesigner.Runtime.ExternalBehavior ExternalBehaviorTree` (public) — the NPC's actual decision-making is a **Behavior Designer** behavior tree (a third-party Unity asset), not a hand-rolled FSM. **If you take over an NPC's `NavMeshAgent` yourself (e.g. to drive it as a custom "unit"), you must disable this behavior tree, or it will keep re-issuing its own destination/stop commands and fight your code.** Symptom this produces: `agent.pathStatus` reports `PathComplete` (a perfectly valid path) but `agent.remainingDistance` never shrinks — the two "brains" are fighting over the same NavMeshAgent every frame.
  - Don't hardcode the field name. Field names can drift between game builds/updates (this bit us once — a reflection lookup for the exact name `"behaviorTree"` came back null after apparently working from an older type dump). Instead, reflect over **all** `FieldInfo` on `AINavMeshHumanoid` and match by *type* — anything whose `FieldType.Namespace` contains `"BehaviorDesigner"` — then cast the value to `UnityEngine.Behaviour` and set `.enabled = false`. This is robust to the exact field name changing.
- `AINavMeshHumanoid.EState` enum: `None, Idle, Sleep, Sick, Captured, Stunned`, with a `EnterRestMode(EState, float)` method. Its exact interaction with movement wasn't verified in this project (it might freeze movement outright) — disabling the behavior tree component directly was the safer, verified approach.
- `AINavMeshHumanoid.CreateHumanoid(GameObject prefab, Vector3 position, bool needsReachPosition, Vector3 reachPosition)` — the game's own static factory for spawning a humanoid from a template `GameObject`. Effectively wraps `Instantiate()`.

**Unity `Object.Instantiate()` copies `activeSelf`.** If your "template" `GameObject` is deliberately inactive (e.g. a hidden permanent clone kept around for later use — see below), then *every* object created from it via `Instantiate()`/`CreateHumanoid()` is also born inactive and does nothing until you explicitly call `.SetActive(true)` on the result. Easy to lose an hour to this.

**A live GameObject cannot be saved to disk from inside a running game.** `AssetDatabase`/`PrefabUtility.SaveAsPrefabAsset` are Editor-only APIs, stripped from the compiled player — a mod has no access to them at runtime. Beyond that, a lot of what makes up a "real" NPC isn't plain serializable data anyway: `Animator` playable graphs, `NavMeshAgent` internal path state, and IK solvers (this game uses FinalIK's `BipedIK`/`GrounderBipedIK`) are engine-managed runtime state that only exists once the object is actually instantiated in a running scene. The practical workaround used in this mod: grab a reference to a real, currently-loaded friendly NPC once, `Instantiate()` a copy of it, `SetActive(false)` + `DontDestroyOnLoad()` it, and keep that hidden clone in memory as a reusable template for the rest of the process's lifetime. This has to be redone once per game launch (nothing persists across a restart), but since it only needs *any* nearby friendly NPC — not a specific one — it can be done opportunistically in the background the first time one is nearby, rather than requiring a deliberate step from the player.
  - Note: a *narrower* form of persistence (e.g. saving which named template/prefab to use, plus stats/gear, as small data — not the live object) is a real, if effortful, custom-serialization option in principle. It wasn't pursued here partly because it wouldn't actually remove the "be near an NPC once" requirement in this specific game: the live instance still doesn't exist in the scene until the engine's own distance-based streaming decides to load one nearby, regardless of what a mod remembers between launches.

**Wagons (`WagonControllerEx`) are the odd one out: no master list, and a physics body.** Items, containers and animals all have a static registry (`ItemBase.AllItems`, `ItemContainer.AllContainers`, `AnimalController.AllAnimals`); wagons have none, so `FindObjectsOfType<WagonControllerEx>()` is the only way to enumerate them — far too expensive for a per-agent, per-frame tick, so cache one shared scan on a timer (3s here). Useful public members, all verified by IL:
  - `RequestedBy` (`System.Object`) — **this is wagon ownership**. `GetWorldGroup()` is nothing but this field cast to `WorldGroup`, so assigning a `WorldGroup` to it is how you hand a wagon to a camp. `WorldGroup.Carts` is *not* an ownership registry — it's a spawn-time count read by `SpawnCoroutine` to decide how many carts to instantiate, so incrementing it would just make the camp spawn an extra cart later.
  - `CanInteract()` — just `Owner == null`, i.e. "nobody is on this wagon". `isPlayerMounted()` is `Owner != null && !isAI`.
  - **`IsAlive()` is a 2-byte stub that always returns `true`** — useless as a destroyed check. Use the `bWagonDead` field instead. (Worth checking for this pattern on other classes before trusting an `IsAlive()`.)
  - `LootContainer` (`ItemContainer`), `Horses` (`WagonControllerEx+Horse[]`, positioned relative to the wagon each frame by `CalculateHorsePosition()`, so they follow it when it's moved), `RB` (`Rigidbody`), `WagonHealth`, `WagonInCampOrOutpost`.
  - Relocating one is not like relocating a horse: it's a `Rigidbody` on `WheelCollider`s. Zero `velocity`/`angularVelocity` first or it arrives still carrying its momentum, set both `transform.position` and `rb.position`, and flatten the rotation to yaw-only (`Quaternion.Euler(0, eulerAngles.y, 0)`) or a wagon captured on a slope arrives tilted.

**NavMeshAgent pathing has several distinct "stuck" failure modes** — this took multiple iterations (and multiple real debug logs) to fully map out, because each one produces the same visible symptom (a unit stands still) for a different underlying reason:

1. `agent.pathStatus == NavMeshPathStatus.PathInvalid` — the "obviously stuck" case, easy to detect directly.
2. `agent.pathStatus == NavMeshPathStatus.PathPartial` — the agent computed a path to the *closest reachable point*, not the actual destination (e.g. a target inside a building interior the navmesh doesn't fully cover). This is **not** reported as invalid — checking only for `PathInvalid` misses it completely, and the agent will walk to that closest point and then just sit there forever, `remainingDistance` never reaching the arrival threshold.
3. `agent.isOnNavMesh == false` — the agent never actually attached to the NavMesh in the first place (can happen if its spawn point is a hair off the nearest navmesh polygon). While this is true, `SetDestination` silently does nothing, forever. A check that bails out early whenever `!isOnNavMesh` (treating it as "not stuck, nothing to report") is backwards — it's actually the worst case, since nothing else will ever catch it.
4. The destination itself is **not reachable/samplable by the NavMesh at all** — e.g. an animal standing inside a stable/pen whose floor isn't covered by the baked navmesh. Here `SetDestination` can fail silently (no exception, just returns without effect): `hasPath` stays `false`, `remainingDistance` reports `Infinity`, and — confusingly — `pathStatus` still reports `PathComplete`, because that's Unity's documented default value for "no path has been calculated yet." Seeing `PathComplete` with `remainingDistance == Infinity` together is the tell for this specific case.

The fix that generalizes across all four cases: don't try to special-case every combination of `pathStatus`/`isOnNavMesh`/`pathPending`. Instead, track `agent.remainingDistance` over time yourself, and if it hasn't meaningfully shrunk (e.g. by more than ~0.15m) within a stall timeout (e.g. 6 seconds) — counting time spent in any of the broken states above as "not shrinking" too — treat the destination as unreachable and move on. Reset this stall tracker every time a *new* destination is assigned, or a stall measured against the previous target will immediately condemn the new one.

For targets that don't need a literal walk-up-and-touch (e.g. this mod's horse capture, which is really a teleport effect, not a physical grab), don't require full arrival at all: use a generous straight-line-distance "close enough" radius, and if the NavMesh genuinely can't route to the target's exact position (case 4 above), fall back to `NavMesh.SamplePosition(target, out hit, radius, NavMesh.AllAreas)` to find the nearest point it *can* reach, retarget there, and apply the straight-line check from that new position.

**`PlayerActions.BurnSettlement(WorldGroup, float duration, ParticleSystem[])`** is the game's own "burn down a camp" coroutine (found by dumping the IL body of the compiler-generated `PlayerActions/<BurnSettlement>c__Iterator25::MoveNext()`, since the decompiled method itself is just a stub). It sets `PlayerActions.interacting = true` and `canMoveOrFaceToDirection = false` at the start, and is *supposed* to restore both and call `EndInteraction()` at the end — but that cleanup does not reliably run to completion in practice, and can leave the player permanently stuck unable to move. Both fields and both `BeginInteraction()`/`EndInteraction()` methods are `public`, so no reflection is needed to call this — but if you use it, also start a parallel watchdog coroutine that force-restores control after a timeout, as a safety net against the cleanup not firing.

**`GameplayEvents`** uses a generic `EventDescription<T>.Subscribe(handler, bool)` / `.Trigger(T data)` pattern (e.g. `CampWillBeBurned`, `CampBurned`, `PlayerCampCreated`, `EntityKilled`). If you manually trigger game behavior that would normally cause one of these events as a side effect of the *normal* player-order flow (like calling `BurnSettlement` directly instead of going through an order), other systems that listen for that event won't know it happened unless you fire the `Trigger` yourself.

**`WorldGroup`** represents a camp/settlement. `WorldGroup.AllGroups` is the static list of all of them. Relevant enums: `EMode` (`Wandering=0`, `Camp=1`) and `EBurnType` (`Burnable=0`, `NonBurnable=1`, `InvisibleToBurn=2`).

**The crafting/item system can be extended at runtime without touching any game files on disk**: clone an existing donor item (e.g. a real "Campfire" `PlaceObjectItem`) via reflection/copy, register the clone into `ItemsDB.Items`, and inject a matching entry into `ItemProduction` (the recipe list) so it's craftable. This is how this mod's fully custom summon item was added. One landmine hit along the way: resizing `ItemsDB.Items` (needed only for making the item assignable as a camp work order) was linked to a crash in testing — that specific sub-feature was kept off-by-default/experimental as a result, while the main item-injection technique itself is solid.

**Anything a mod injects into the game's own singletons is wiped when a save is loaded — inject continuously, never once.** This bit the craftable-item feature in two separate ways, and the shape generalises to any runtime injection in this game:
  - `ItemRequirements` (the recipe list) and `ItemsDB` (the master item list) are both **MonoBehaviour singletons living in the scene**. Loading a save reloads the scene, so both are reconstructed from their serialized originals and anything appended at runtime is gone. A mod that injects once and latches a `bool injected = true` will silently lose its content on the first save load and never notice. The fix is a cheap presence check on an existing periodic tick (`does the live array still contain my entry?`) that re-injects when it doesn't.
  - `MissionExtensions.LearnItemRequirement(item)` does **not** store the item. It resolves the item to its `ProductionDescription`, takes that description's **index in `ItemRequirements.Instance.ItemProduction`**, and appends that `int` to `WorldState.Instance.KnownItemRequirements` — which is save data. So "known recipes" is a list of array positions, restored from the save, pointing into an array the mod has to rebuild. Re-injecting in a deterministic order puts the entry back at the same index, which is why it lines up. Guard the re-learn with `MissionExtensions.KnowItemRequirement(item)`: `LearnItemRequirement` also calls `InformationalScreen.AddSideMessage`, so calling it unconditionally on a timer spams an on-screen "learned!" toast.
  - **`ItemBase.PrefabPath` is an item's cross-session identity.** `ItemBase.Awake()` resolves `Prefab` by looking `PrefabPath` up in the private static `pathToPrefab` dictionary. A cloned item given a `Guid.NewGuid()` path (as this mod originally did) therefore gets a brand-new identity every launch, and any instance of it saved in the player's inventory can never be resolved again — it just disappears. Use a fixed constant path, re-seed `pathToPrefab` with it on every injection, and `DontDestroyOnLoad` the clone so a scene load doesn't destroy the object that path points at. Note the migration cost: changing this value orphans items saved under the old one.
  - Related trap already documented above: `ItemBase.EqualsTo` compares by `Prefab` reference, so the clone still needs its *own* distinct `Prefab`/`PrefabPath` from the donor — "fixed" must not mean "same as the donor's".

**Check for a native game feature before building a custom one.** This project built and fully debugged a custom "auto-burn the nearest cleared camp" feature (including a coroutine watchdog for a stuck-player bug it introduced) before discovering the game already has a built-in Orders-UI option — "loot and burn cleared nearby enemy camps" — that does the same thing more simply and reliably. Worth a deliberate look at the game's own UI/systems before reimplementing something that sounds like core gameplay.

**Camps carry the character *prefabs* their people are spawned from, and that is the streaming-proof way to get an NPC template.** `WorldGroup` (a camp) has a public `Entity[] EntityPrefabs`, plus `String[] AvailableCharacterCustomizations`. The game's own `WorldGroup+UnitsDescription.CreateUnit` and `WorldGroup+<SpawnCoroutine>c__Iterator3.MoveNext` both work off these: pick a random element of `Owner.EntityPrefabs`, `Instantiate` it, `CharacterCustomization.ApplyPreset(name, System.Random)`, then `Entity.SetFaction(group.Faction)`. All of those members are public.
  - This matters because a *prefab is an asset, not a scene object*: distance-based streaming never unloads it, it can't die, and once a mod holds a reference it stays valid for the whole session even if every camp in the world unloads. That makes it strictly better than the hidden-live-clone trick above for "I need an NPC template and there may be nobody loaded anywhere near me" — which is the normal case out between camps, and was this mod's single most persistent complaint (v7.10 through v7.15 are all attempts at the same problem from the live-NPC side, and none of them removed the underlying requirement).
  - Faction is the reason the older code refused to clone just any humanoid. That concern dissolves once you call `Entity.SetFaction(playerFaction)` on the spawned instance yourself: a prefab from an enemy camp then produces a warrior on *your* side who merely looks like someone else's people. Order matters — `Entity.Awake()` calls `InitializeStatusVariables()` and re-applies the template's own serialized faction, so `SetFaction` has to come *after* the `SetActive(true)` that runs Awake, or it gets silently overwritten.
  - `Entity.Awake()` calling `InitializeStatusVariables()` is also why a prefab needs no health/status setup of its own. Don't run an `IsAlive()` check against a prefab, though — it has never had Awake run, so it reads as not alive; check only that it has an `AINavMeshHumanoid`.
  - `WorldGroup.AllGroups`/`FriendlyGroups` are populated in `WorldGroup.OnEnable` and cleared in `OnDisable`, so camps themselves can stream out too. Grab the prefab reference opportunistically while camps are loaded and hold onto it; the reference outlives the camp that provided it.

**Skills are `Ability` MonoBehaviours, and the whole input path is public — no patching needed to add hotkeys.** The player's skills are `entity.KnownAbilities` (`List<Ability>` on `Entity`), and everything the game does with them goes through members a mod can call directly (verified by IL, and the basis of the `SkillHotkeys` plugin):
  - `PlayerActions.Update()` clamps `ActiveAbilitySlot`, then compares `KnownAbilities[ActiveAbilitySlot]` against the private `lastAbility` and, when they differ, calls `OnUnequip(entity)` on the old one and `OnEquip(entity)` on the new one. **Assigning `ActiveAbilitySlot` is therefore the entire act of "selecting" a skill** — it is all `ShowAbilitySelectionWheel()`'s click handler does — and it is what makes a `Passive` ability (`SlowTimeAbility`) take effect. Equip runs in *that* `Update`, so if you select a slot and use it in the same frame, MonoBehaviour order decides whether `OnEquip` ran first; deferring the use by one frame removes the question.
  - `PlayerActions.LateUpdate()` is just `if (AbilityPress) UseAbility(ActiveAbilitySlot);`, plus `ShowAbilitySelectionWheel()` on `AbilitySlot.HoldBinding`.
  - `PlayerActions.UseAbility(int)` (public, returns bool) indexes `KnownAbilities`, checks `!interacting`, `!characterWeaponController.Aiming`, bounds, null, and `RealisticDamageHandler.AbilityAllowed`, then starts the use coroutine. `Ability.CanBeUsed(Entity)` / `CantBeUsedReason(Entity)` are public and virtual, so the same gate the HUD shows can be queried up front.
  - **The catch: the coroutine's "keep using" loop polls `PlayerInputManager.Instance.AbilityHold` every iteration.** Any non-`InstantUse` ability (tomahawk, spyglass, distract, wait) started from a different key ends on its first frame, because the game's own ability button isn't down. The fix is one field: `PlayerInputManager+InputBinding.ForceActive` is public and is the *first* thing `InputBinding.Active()` tests, so setting `AbilityHold.ForceActive = true` for as long as your own key is held makes the game behave exactly as if its button were pressed. Always pair it with a release path that survives the unexpected (key up, `ActiveAbility` going back to null, and a hard timeout) — a stuck `ForceActive` is a stuck ability button for the rest of the session.
  - `SelectionWheelHandler.ActiveSelectionWheel` is a public static reference to the open wheel (null when none) — the cheap "is the player in a wheel right now" check. For "is the player typing", look at `EventSystem.current.currentSelectedGameObject` and match component type names containing `InputField`, which covers both uGUI and TextMeshPro without referencing either.
  - `PlayerInputManager.AllBindings` is a public *static* `List<InputBinding>`, so a mod can enumerate the game's bindings without an instance. Its `Key` field is only the built-in default though — actual binds live in Rewired — so it is good for a best-effort conflict warning, not for authoritative "what is this key bound to".

**Skill names only exist at runtime.** `Ability` extends `ResourceBasedBehaviour`, whose `Name` is a localization key resolved through `StringExtensions.Localize`, and the display strings live in serialized assets, not in any DLL. A mod that wants per-skill config entries cannot pre-declare them from a type dump — bind them at runtime from `KnownAbilities` on a periodic tick (which also covers skills learned mid-session and the list being rebuilt on save load), and use `ability.name` with the class name as fallback for a stable config key.

## General debugging lessons (apply beyond this specific game)

- Reproduce root cause from a real log/data sample before extending a hypothesis further. Several early theories in this project (a registration-timing race, a missing component type) were dropped, not confirmed, once real diagnostic output came back — don't keep building on a guess once evidence contradicts it.
- Add a hard safety-net timeout for anything that waits on an external system you don't fully control (pathfinding, a coroutine you didn't write, streamed data). It turns a "stuck forever, session never ends" bug into a "recovers after N seconds" bug while you find and fix the actual cause.
- When a fix "sort of" works or the symptom is intermittent/timing-sensitive, it's worth asking about anything that changes effective time scale (a fast-forward/time-skip feature, frame-rate drops) — but don't let that become the default explanation; in this project every one of the real bugs turned out to be a distinct, fixable root cause rather than a timing artifact, and treating "maybe it's just timing" as the answer would have left them all unfixed.


## Build scripts

Two are recorded here because the toolchain moved. `compile.sh` (below) was the original, run from a Linux dev environment with Mono's `mcs`. `build.ps1` is the current one and runs entirely on the user's own Windows machine.

### `build.ps1` (current, Windows, no SDK required)

The Windows machine has **no .NET SDK and no Visual Studio**. The only in-box compiler is `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`, which is pre-Roslyn and understands **C# 5 only** — and this mod's source is C# 6/7 (string interpolation throughout, one `out` variable declaration). Rewriting ~2400 lines down to C# 5 turned out to be unnecessary, because:

**The game ships Roslyn 2.10 in its own `Managed` folder** (`Microsoft.CodeAnalysis.dll` + `Microsoft.CodeAnalysis.CSharp.dll` — it embeds RoslynCSharp for runtime scripting), along with Roslyn's own dependencies (`System.Collections.Immutable`, `System.Reflection.Metadata`). Driving that gives full C# 7.3 with nothing to install. Gotchas found doing it:

- That Roslyn is a **netstandard** build. Compiling a driver program *against* it fails with a wall of `CS0012 ... 'System.Runtime'` errors unless the .NET Framework reference facades are installed, and they aren't on this machine (no `Reference Assemblies\...\Facades` folder). The fix is to **late-bind everything** — PowerShell calling Roslyn through normal method syntax works fine, because at *runtime* the CLR unifies those facades to mscorlib.
- There is **no `Compilation.Emit(string path)` overload**. The smallest is `Emit(Stream, Stream, Stream, Stream, IEnumerable, EmitOptions, CancellationToken)` — open a `FileStream` and pass nulls.
- An `AssemblyResolve` handler that calls `Assembly.LoadFrom` **re-enters itself for the same name and overflows the stack**. Guard it with a flat hashtable of names currently being resolved, and don't use pipelines inside the handler.
- Compiling against the game's `Managed\mscorlib.dll` while referencing Unity/BepInEx assemblies built against mscorlib 2.0.0.0 produces **thousands of CS1701/CS1702** warnings. They're noise (the runtime unifies them — it's what the game itself does at load), so suppress them via `CSharpCompilationOptions.WithSpecificDiagnosticOptions`.
- `LanguageVersion.CSharp6` is not enough: the source has an `out` variable declaration, so use `CSharp7_3`.

`build.ps1 -Deploy` refuses to copy into `BepInEx\plugins` while the game is running. BepInEx loads plugin DLLs from bytes rather than mapping them, so the file *isn't* locked and the copy would silently succeed while the running game kept the old code — the guard exists to stop exactly that confusion.

A related trick worth reusing: the same "load the game's assemblies and reflect" approach regenerates `all_types.txt` from PowerShell in one pass (`Assembly.LoadFrom` each `Managed\*.dll`, catch `ReflectionTypeLoadException` and use its `.Types`), and decoding a method body's IL for the `call`/`callvirt`/`ldfld`/`ldsfld` opcodes (`0x28/0x6F/0x7B/0x7E`, each followed by a 4-byte metadata token passed to `Module.ResolveMember`) is enough to answer "what does the game's own code actually call here?" without a decompiler — that is how the `EntityPrefabs` spawn path above was confirmed.

### `compile.sh` (original, Linux/Mono)

```bash
#!/bin/bash
set -e
REFS=/tmp/tliml_mod/refs
```
